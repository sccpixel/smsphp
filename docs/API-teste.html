SMS Gateway API

API REST em JSON para enviar SMS e pedir aprovações a gestores por SMS (descontos, movimentos de armazém, etc.). Destinada a quem desenvolve APPs que a utilizam.

#1. Conceitos

A API não envia o SMS na hora. Valida o pedido, guarda-o numa fila e responde logo (201). Um processo à parte passa a mensagem ao programa de SMS, que a envia pelo modem. Por isso, o 201 quer dizer "recebido e na fila", não "entregue". Para saber o que aconteceu a seguir, consulta o estado (GET).

Aprovações. A APP pede a aprovação de algo; a API envia um SMS ao gestor com um código de 4 dígitos; o gestor responde SIM 4821 ou NAO 4821; a APP consulta o resultado.

#2. Começar

#URL base

AmbienteURL
Testes (este documento)https://mild-funky-sorry-banner.trycloudflare.com
Este endereço é só para testes e é temporário. É um túnel de teste da Cloudflare: muda sempre que o túnel é reiniciado e deixa de funcionar quando é fechado. Não o guardes em código nem em configuração definitiva: o administrador avisa quando houver o endereço permanente (só se troca o URL base, o resto da documentação mantém-se).

#Autenticação

Todas as rotas /api/* exigem uma chave no header X-API-Key.

  • A chave pede-se ao administrador. Cada aplicação deve ter a sua.
  • Só no header. A chave na URL (?api_key=...) não é aceite, porque ficaria nos logs.
  • Guarda a chave no servidor da APP; nunca a coloques em código que corra no browser ou no telemóvel do utilizador final.
  • O administrador pode também limitar os IPs que podem usar a API.

GET /health é público (não pede chave).

#Formato dos pedidos

  • Enviar JSON com Content-Type: application/json. Também são aceites formulários (application/x-www-form-urlencoded).
  • As respostas são sempre JSON em UTF-8.
  • Datas: AAAA-MM-DDTHH:MM:SS, sem fuso horário, hora de Portugal (ex.: 2026-10-15T10:00:00).

#Números de telefone

Qualquer um destes formatos é aceite e dá o mesmo resultado (912345678):

+351912345678 · 00351912345678 · 351912345678 · 912345678 · +351 912 345 678 (espaços, hífenes e parênteses são ignorados)

Só números portugueses: um número com outro indicativo (+44...) é rejeitado com 422. A API guarda e envia o número sem +351.

#Verificar que está tudo vivo

GET/health

200 se estiver tudo bem; 503 com "status": "degraded" se a base de dados não responder.

#3. Mensagens (SMS)

#Criar uma mensagem

POST/api/messages
CampoTipoObrigatórioRegras
totextosimnúmero português (ver acima)
texttextosim1 a 255 caracteres (espaços nas pontas são removidos)
instance_nametextonãoaté 255 caracteres; identifica o modem/instância, se houver mais de um. Se faltar, fica sem valor e é o programa de SMS que decide

Resposta 201

Guarda o id: serve para consultar o estado.

Um SMS com mais de 160 caracteres (ou 70, se tiver acentos ou símbolos fora do alfabeto GSM) é enviado em várias partes pelo operador. A API aceita até 255 caracteres.

#Criar várias mensagens (lote)

POST/api/messages/batch
  • Entre 1 e 500 mensagens.
  • Tudo ou nada: se alguma for inválida, nenhuma é gravada e recebes 422. Os erros identificam a posição (começa em 0): "messages.2.to": "Número de telefone inválido".

Resposta 201

#Consultar uma mensagem

GET/api/messages/{id}

Resposta 200

CampoSignificado
queue_statuspending — ainda não foi passada ao programa de SMS · dispatched — já foi passada · failed — não foi possível passá-la (ver error)
send_statusEstado do envio pelo programa de SMS: null enquanto não foi passada; 0 por enviar; 2 erro no envio. Outros valores são do programa de SMS (o envio concluído aparece com sent_at preenchido)
sent_atQuando o programa de SMS a enviou (null até lá)
errorMotivo, se queue_status for failed

Dá 404 se o id não existir.

Como saber se foi mesmo enviada? Quando sent_at está preenchido. Se send_status = 2, o envio falhou. Enquanto send_status for 0, ainda está à espera do modem.

#4. Aprovações

#Estados de um pedido

statusSignificadoFinal?
pendingÀ espera da resposta do gestornão
approvedO gestor respondeu SIMsim
rejectedO gestor respondeu NAOsim
expiredPassou o prazo sem respostasim
cancelledA APP cancelousim

Só se sai de pending; os restantes são finais.

#Criar um pedido

POST/api/approvals
CampoTipoObrigatórioRegras
typetextosimcódigo de um tipo ativo (ver tipos), ex.: discount, stock_move
descriptiontextosim1 a 120 caracteres; é o que o gestor lê no SMS
referencetextonãoaté 100 caracteres; o identificador do pedido na vossa APP (ex.: VENDA-1234)
requested_bytextonãoaté 100 caracteres; quem pediu (ex.: o operador)
manager_idinteirosimid do gestor que decide, obtido em GET /api/managers. Tem de existir e estar ativo. Não há gestor por defeito: a API serve várias aplicações e cada pedido diz sempre a quem vai
callback_urlURLnãoaté 255 caracteres. Endereço da APP que o gateway avisa (POST) quando o pedido é aprovado, rejeitado ou expira. Tem de ser https:// e público (ver Avisos automáticos)

Resposta 201

O gestor recebe:

Pedido 4821 - Desconto: 15% na venda 1234, cliente Silva. Responda SIM 4821 ou NAO 4821. Valido 10 min.
  • O SMS vai para o telefone guardado no gestor; a APP nunca indica números.
  • O texto do SMS não leva acentos nem caracteres especiais (João → Joao), para caber num só SMS. A description guardada e devolvida pela API mantém o texto original.
  • O code é único entre os pedidos pendentes. Não é preciso que a APP o mostre ao utilizador, mas pode ser útil para o operador.
  • O prazo (expires_at) é configurado no servidor (por defeito, 10 minutos).

#Consultar um pedido

GET/api/approvals/{id}

Resposta 200

CampoSignificado
statusVer tabela de estados. Se o prazo já passou e ninguém respondeu, vem logo expired
responded_at, response_textQuando e o que o gestor respondeu (null se ainda não respondeu)
sms_statusEstado do SMS enviado ao gestor: pending — ainda não saiu · sent — enviado · failed — nunca chegou ao gestor
callback_statusEstado do aviso à tua APP: none — o pedido não tem callback_url (ou ainda não foi decidido) · pending — à espera de ser enviado ou de nova tentativa · sent — a APP respondeu 2xx · failed — o gateway desistiu (a APP continua a poder consultar o pedido)

Importante: se sms_status for failed, o gestor nunca viu o pedido. O status continua pending até expirar, por isso a APP deve tratar este caso (avisar o operador, cancelar e tentar de novo, escolher outro gestor).

Dá 404 se o id não existir.

#Saber o resultado

Há duas formas, que podem ser usadas em conjunto:

  1. Consultar: a APP chama GET /api/approvals/{id} de 3 em 3 segundos (não menos), até o status

deixar de ser pending, ou até o utilizador desistir. Funciona sempre, em qualquer APP.

  1. Ser avisada (callback): se o pedido tiver callback_url, o gateway chama esse endereço assim que o

pedido é decidido. Evita consultas constantes. Ver a secção seguinte.

#Avisos automáticos (callback)

Ao criar o pedido, indica o callback_url (https://, público). Quando o pedido passa a approved, rejected ou expired, o gateway faz um POST a esse endereço. Um cancelamento não gera aviso (foi a própria APP que o pediu).

O que a APP recebe

O corpo é o mesmo de GET /api/approvals/{id}, mais o campo event. Usa o reference para saber a que operação da tua APP o pedido corresponde.

O que a APP tem de fazer

  • Responder com HTTP 2xx (por exemplo 200), em menos de 5 segundos. Qualquer outra resposta, ou

falta de resposta, conta como falha. Os redirecionamentos (301, 302...) não são seguidos.

  • Verificar a assinatura antes de confiar no conteúdo (qualquer pessoa pode fazer um POST ao teu

endereço). A assinatura é um HMAC-SHA256 de <timestamp>.<corpo> com a chave de API da tua APP como segredo. Usa sempre o corpo em bruto, tal como chegou, antes de o converter em JSON. Exemplos abaixo.

  • Tratar avisos repetidos: o gateway garante a entrega "pelo menos uma vez". Se a APP responder tarde e o gateway

repetir, o mesmo aviso chega duas vezes. Faz o tratamento de forma que receber o mesmo status outra vez não estrague nada (o X-Gateway-Delivery identifica cada tentativa: <id do pedido>-<n.º da tentativa>).

Exemplo de verificação (PHP)

Exemplo de verificação (Node.js)

Se a APP falhar: o gateway repete 6 vezes, com esperas de 1, 2, 5, 10, 20 e 30 minutos (7 tentativas em cerca de 1 hora). Se mesmo assim não conseguir, desiste (callback_status: "failed") e a APP continua a poder consultar o pedido com GET. Por isso, não dependas só do callback para pedidos importantes: confirma com um GET se passou muito tempo.

Regras para o endereço (recusadas com 422 ao criar o pedido):

  • tem de começar por https://;
  • tem de ser público: não pode ser localhost, um IP privado (192.168.x.x, 10.x.x.x, 172.16-31.x.x) nem um

nome interno (sem ponto, .local, .lan);

  • não pode ter utilizador e password no endereço (https://user:pass@...);
  • até 255 caracteres.

Se a tua APP está na rede interna da empresa e não tem um endereço público, o callback não a alcança: fala com o administrador (existe uma opção para aceitar redes internas) ou usa só a consulta (GET).

#Cancelar um pedido

POST/api/approvals/{id}/cancel

Sem corpo. Responde 200 com o pedido já atualizado ("status": "cancelled").

  • 404 — o pedido não existe.
  • 409 — o pedido já não está pendente (já foi respondido, expirou ou foi cancelado).

Cancelar não envia nenhum SMS ao gestor. Se ele responder depois, recebe Pedido 4821 ja estava cancelado.

#O que o gestor pode responder

O gestor responde por SMS ao número que enviou o pedido:

RespostaEfeito
SIM 4821aprova
NAO 4821 ou NÃO 4821rejeita
  • Maiúsculas/minúsculas e o acento de "não" são indiferentes.
  • O formato é exato: SIM sozinho, OK 4821, SIM 4821 obrigado, SIM 4821 4822 e semelhantes não são reconhecidos e são ignorados (o gestor não recebe resposta).
  • Só respostas vindas de gestores ativos são consideradas; SMS de outros números são ignorados.
  • O gestor recebe uma confirmação: Pedido 4821 aprovado. / Pedido 4821 rejeitado., ou um aviso (ja estava aprovado/expirado/cancelado, nao encontrado).

#5. Gestores e tipos de pedido

Só leitura. A gestão (criar, desativar, alterar) é feita pelo administrador.

#Gestores

GET/api/managers

Só os ativos. Não devolve o número de telefone.

Cada pedido de aprovação tem de indicar o manager_id de um destes gestores (é obrigatório). O campo is_default existe só por compatibilidade e não tem efeito nos pedidos: ignora-o.

#Tipos de pedido

GET/api/approval-types

Usa o code no campo type do pedido. Só os tipos ativos.

#8. Boas práticas

  • Verifica sempre o código HTTP antes de usar a resposta. Em 422, mostra ao utilizador os details.
  • Consulta o estado, não assumas. 201 significa "na fila". Para confirmar o envio, consulta GET /api/messages/{id}; para saber a decisão, GET /api/approvals/{id}.
  • Consulta de 3 em 3 segundos, no máximo, e para quando o estado for final.
  • Trata sms_status: "failed" nas aprovações: o gestor nunca recebeu o pedido.
  • Não repitas pedidos às cegas. A API não tem proteção contra duplicados: se repetires um POST por não teres recebido a resposta, podes criar duas mensagens ou dois pedidos. Antes de repetir, confirma se o primeiro chegou (por exemplo, guardando a reference do pedido do lado da APP).
  • Não uses a API para enviar a números que não controlas em massa sem falar com o administrador: tudo passa por um modem 3G, com limites do operador.
  • Timeout de 10 segundos nas chamadas à API é suficiente; a API responde de imediato (nunca espera pelo envio).
  • Guarda a chave em segredo e pede outra ao administrador se suspeitares que foi exposta.
